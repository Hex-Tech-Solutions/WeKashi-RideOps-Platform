 CRITICAL (must fix before launch)
════════════════════════════════════════════════════════════════════════════════

[C1] DEV_OTP_BYPASS IN PROD ENV EXAMPLE
  File: .env.prod.example (line: DEV_OTP_BYPASS=123456)
  Issue: The production env example still has DEV_OTP_BYPASS=123456 set.
         If this is copied to .env.prod without removing it, ANY driver can
         log in with OTP "123456" — completely bypassing SMS authentication.
  Fix:  DELETE the DEV_OTP_BYPASS line entirely from .env.prod.example and
        ensure it is not present in any live .env.prod file.

[C2] JWT SECRETS FALL BACK TO HARDCODED DEV STRINGS
  File: backend/src/lib/jwt.ts
  Code: const ACCESS_SECRET = process.env.JWT_ACCESS_SECRET ?? 'dev-access-secret';
        const REFRESH_SECRET = process.env.JWT_REFRESH_SECRET ?? 'dev-refresh-secret';
  Issue: If the API container starts without the env file (e.g., misconfigured
         deploy), it silently uses known-public secrets. An attacker could mint
         valid tokens for any user/role.
  Fix:  Throw a startup error if either secret is missing or equals a known
        default. Example:
          if (!process.env.JWT_ACCESS_SECRET) throw new Error('JWT_ACCESS_SECRET is not set');

[C3] NO HTTPS / TLS IN NGINX CONFIG
  File: docker/nginx.conf
  Issue: Nginx listens on port 80 (plain HTTP) only. All auth tokens, OTPs,
         and sensitive data travel unencrypted over the wire in production.
  Fix:  Add TLS termination — either via Nginx with Let's Encrypt/certbot,
        or via an AWS ALB / Cloudflare proxy in front of the EC2 instance.
        Update CORS_ORIGIN and all env URLs to https://.

[C4] CORS DEFAULTS TO WILDCARD '*'
  File: backend/src/sockets/index.ts + backend/src/app.ts (via env)
  Code: origin: process.env.CORS_ORIGIN ?? '*'
  Issue: If CORS_ORIGIN is not set, both HTTP and WebSocket connections are
         accepted from any origin, enabling CSRF-style attacks.
  Fix:  Throw a startup error if CORS_ORIGIN is not set in production.
        Never allow '*' in a production build.

 HIGH SEVERITY (authorization & access control gaps)
════════════════════════════════════════════════════════════════════════════════

[H1] GET /drivers/:id — NO OWNERSHIP / ROLE GUARD
  File: backend/src/routes/drivers.ts
  Issue: Any authenticated user (any role) can look up any driver by ID.
         A supervisor can enumerate all vendor drivers; a driver could look
         up other drivers. Exposes phone numbers, vehicle info, location, etc.
  Fix:  Add a role check — only vendor (own drivers), admin, or the driver
        themselves should be able to call this endpoint.

[H2] GET /rides/:id — NO ROLE GUARD
  File: backend/src/routes/rides.ts
  Issue: Any authenticated user can fetch any ride's full detail including
         passenger list, driver info, and route. A driver can see rides
         belonging to other vendors/supervisors.
  Fix:  Add ownership scoping: supervisor can only fetch their own rides,
        driver can only fetch rides they are assigned to, vendor only their
        rides. Admin sees all.

[H3] PATCH /rides/:id/status — NO ROLE GUARD ON THE ROUTE ITSELF
  File: backend/src/routes/rides.ts
  Issue: The status-advance endpoint has no requireRole() guard. The
         permission logic lives inside advanceRideStatus() service, but
         there is no middleware-level gate. An unauthenticated bypass or
         role confusion could reach the service with an empty requestorRole.
  Fix:  Add requireRole('driver', 'supervisor', 'admin') at the route level
        so the service never receives an empty role string.

[H4] SAFETY INCIDENT — ANY AUTHENTICATED USER CAN CREATE
  File: backend/src/routes/safety.ts  (POST /safety/incidents)
  Issue: The POST route has no requireRole() guard — any authenticated user
         (including a vendor or an unrelated driver) can create a safety
         incident for any rideId. There is also no check that the reporter
         is actually related to the referenced ride.
  Fix:  Add requireRole and validate that the reportedBy user is the assigned
        driver or the supervisor of the referenced ride.

[H5] ISSUE MESSAGES — DRIVERS CANNOT ACCESS BUT ROLE CHECK IS INCOMPLETE
  File: backend/src/routes/issues.ts  (GET/POST /:id/messages)
  Issue: assertCanAccessIssue uses req.user, but drivers (req.driver) are
         never checked. A driver authenticating as a user (role confusion) or
         a bug in assertCanAccessIssue could expose issue threads.
  Fix:  Verify assertCanAccessIssue handles all roles correctly and covers
        the driver identity path.

[H6] VENDOR CAN SET ARBITRARY userId WHEN CREATING A VENDOR RECORD
  File: backend/src/routes/vendors.ts  (POST /vendors)
  Issue: The VendorSchema accepts a userId field from the request body,
         allowing an admin to (accidentally or maliciously) link a vendor
         record to any existing user — including another admin or supervisor.
  Fix:  userId should be derived from the created user account, not accepted
        as a free-form body field. Remove it from VendorSchema or validate
        that the target user has role 'vendor'.

 HIGH SEVERITY (data & financial)
════════════════════════════════════════════════════════════════════════════════

[H7] VENDOR PAYOUT DETAILS (BANK INFO) STORED UNENCRYPTED
  File: backend/prisma/schema.prisma  (Vendor.payoutDetails Json)
  Issue: Bank account numbers, IFSC codes, UPI IDs etc. are stored as plain
         JSON in the database. A DB dump or SQL injection leaks this directly.
  Fix:  Encrypt the payoutDetails field at the application layer before
        writing to DB (e.g., AES-256-GCM with a KMS-managed key), or use a
        dedicated secrets store.

[H8] DRIVER WALLET BALANCE CAN GO NEGATIVE
  File: backend/src/services/ride.service.ts  (driverReleaseScheduledRide)
  Code: prisma.driver.update({ data: { walletBalance: { decrement: fine } } })
  Issue: There is no check that walletBalance >= fine before decrementing.
         Repeated scheduled-ride releases will push balance arbitrarily
         negative with no floor.
  Fix:  Check current balance before applying the fine, or add a DB
        constraint (walletBalance >= 0) and handle the constraint error
        gracefully.

[H9] PRICE OVERRIDE ON MANUAL ASSIGN IS UNCAPPED
  File: backend/src/services/ride.service.ts  (manualAssignRide)
  Issue: Supervisors and admins can pass any positive number as the price
         override (z.number().positive()). There is no upper-bound validation
         or audit log for price changes.
  Fix:  Add a reasonable maximum (e.g., 10× computed fare), log every price
        override with the requestor's ID, and consider restricting overrides
        to admin-only.

[H10] RAZORPAY WEBHOOK HANDLER IS MISSING
  File: (does not exist yet)
  Issue: RAZORPAY_WEBHOOK_SECRET is in the env example and Razorpay fields
         exist in the Ride schema, but there is no webhook endpoint to
         confirm payment. Without signature verification, the payment flow
         cannot be trusted.
  Fix:  Implement POST /api/payments/webhook with Razorpay signature
        verification (x-razorpay-signature header) before enabling payments.

 MEDIUM SEVERITY (security hardening)
════════════════════════════════════════════════════════════════════════════════

[M1] PAX OTPs ARE ONLY 4 DIGITS (9,000 COMBINATIONS)
  File: backend/src/services/ridePax.service.ts
  Code: const gen4 = () => String(Math.floor(1000 + Math.random() * 9000));
  Issue: With 4-digit OTPs there are only 9,000 possible values. Although
         capped at 5 attempts per OTP, a determined attacker has a 1-in-1,800
         chance per attempt. For a high-value corporate transport context,
         6 digits is safer and expected.
  Fix:  Switch to 6-digit OTPs (100,000 combinations) and ensure the pax
        OTP schema validation is updated (currently allows 4–6).

[M2] Math.random() USED FOR OTP GENERATION — NOT CRYPTOGRAPHICALLY SECURE
  File: backend/src/lib/otp.ts  +  backend/src/services/ridePax.service.ts
  Code: Math.floor(100000 + Math.random() * 900000)
  Issue: Math.random() is not a CSPRNG. On Node.js this is a minor risk in
         practice, but best practice for security codes is crypto.randomInt().
  Fix:  Replace with:
          import { randomInt } from 'crypto';
          const otp = String(randomInt(100000, 999999));

[M3] REFRESH TOKEN ENDPOINT HAS NO RATE LIMITER
  File: backend/src/routes/auth.ts  (POST /auth/refresh)
  Issue: Unlike /auth/login and OTP endpoints, /auth/refresh has no rate
         limiter. An attacker who steals a refresh token can hammer the
         endpoint indefinitely to keep issuing new access tokens.
  Fix:  Apply authRateLimiter (or a dedicated refreshRateLimiter) to
        POST /auth/refresh.

[M4] NO SECURITY HEADERS (helmet)
  File: backend/src/app.ts
  Issue: The Express app does not set security headers: no Content-Security-
         Policy, X-Frame-Options, X-Content-Type-Options, HSTS, etc.
  Fix:  Add `helmet` middleware:
          import helmet from 'helmet';
          app.use(helmet());

[M5] FILE UPLOAD — NO VIRUS/MALWARE SCANNING
  File: backend/src/lib/storage.ts
  Issue: KYC documents (PDFs, images) are accepted and stored without any
         malware scanning. A malicious file could be stored on the server
         volume.
  Fix:  Integrate a scanning step (e.g., ClamAV via clamscan npm package, or
        an AWS Macie/S3 scan) before finalizing the upload. Alternatively,
        move uploads to S3 with server-side scanning enabled.

[M6] UPLOADED FILES SERVED FROM DISK — SHOULD USE CLOUD STORAGE
  File: backend/src/lib/storage.ts  +  routes/files.ts
  Issue: Documents are stored on a Docker volume and served directly by the
         API process. This creates I/O contention, doesn't scale horizontally,
         and the volume must be manually backed up.
  Fix:  Move file storage to AWS S3 (or similar). Generate pre-signed URLs
        for access instead of proxying files through Express.

[M7] STALE REFRESH TOKENS NOT PERIODICALLY PURGED
  File: backend/prisma/schema.prisma  (RefreshToken table)
  Issue: Revoked and expired refresh tokens accumulate in the refresh_tokens
         table indefinitely. Over time this degrades query performance and
         increases the DB backup size.
  Fix:  Add a scheduled cleanup job (cron or DB trigger) to delete tokens
        where revokedAt IS NOT NULL OR expiresAt < NOW().

 MEDIUM SEVERITY (infrastructure & ops)
════════════════════════════════════════════════════════════════════════════════

[M8] REDIS HAS NO AUTH / PASSWORD
  File: docker-compose.prod.yml  (redis service)
  Issue: The Redis container is started with no requirepass setting. Any
         process on the same Docker network can read/write Redis, including
         OTP rate-limit counters and broadcast keys.
  Fix:  Set a strong Redis password via REDIS_PASSWORD env var, update the
        redis service command to `redis-server --requirepass ${REDIS_PASSWORD}`,
        and update REDIS_URL to redis://:password@redis:6379.

[M9] POSTGRES RUNS WITH DEFAULT CREDENTIALS IN PROD EXAMPLE
  File: .env.prod.example
  Code: POSTGRES_USER=rideops / POSTGRES_PASSWORD=CHANGE_ME_strong_db_password
  Issue: The example explicitly labels the password as a placeholder. If an
         operator forgets to change it, the DB is accessible with a guessable
         password.
  Fix:  Generate and document a strong password requirement. Consider
        automating secret generation in the deploy pipeline.

[M10] SINGLE EC2 / SINGLE POINT OF FAILURE
  File: docker-compose.prod.yml
  Issue: The entire stack (DB, Redis, API, Web) runs on one EC2 instance with
         no redundancy. A single instance failure takes down the platform.
  Fix:  For production: use RDS (managed Postgres with Multi-AZ), ElastiCache
        (managed Redis), and at least 2 API containers behind an ALB.

[M11] NO DB BACKUP STRATEGY DOCUMENTED
  File: docker-compose.prod.yml  (pgdata volume)
  Issue: PostgreSQL data is on a Docker named volume with no automated backup
         or point-in-time recovery configured.
  Fix:  Schedule daily pg_dump to S3, or switch to RDS with automated backups.

[M12] PRISMA MIGRATE DEPLOY RUNS ON EVERY BOOT
  File: docker-compose.prod.yml  (api command)
  Code: sh -c "npx prisma migrate deploy && node dist/server.js"
  Issue: Running migrations on every container start is a risk with rolling
         deployments — if two instances start simultaneously they can race on
         the same migration.
  Fix:  Run migrations as a one-off init container or a separate deploy step
        before rolling out the new API version.

 LOW / POLISH (UX, reliability, code quality)
════════════════════════════════════════════════════════════════════════════════

[L1] SUPABASE CLIENT LEFT IN FRONTEND (DEAD CODE)
  File: src/integrations/supabase/
  Issue: Auto-generated Supabase integration files exist but are not used.
         They add bundle size and may confuse future developers.
  Fix:  Delete the supabase integration directory and remove any stale imports.

[L2] DRIVER isOnline STATE CAN DESYNC
  File: backend/src/sockets/index.ts
  Issue: Driver online status is set to true on socket connect and false on
         disconnect. If the server restarts while drivers are connected, all
         drivers remain marked online in the DB forever (no cleanup on boot).
  Fix:  On server startup, run:
          UPDATE drivers SET is_online = false WHERE is_online = true;
        Or use a Redis presence key with TTL that the driver must heartbeat.

[L3] BROADCAST SWEEPER — NO DISTRIBUTED LOCK
  File: backend/src/lib/broadcastSweeper.ts
  Issue: If two API instances run simultaneously (future horizontal scale),
         both sweepers will race to expire the same rides, causing duplicate
         socket emissions and double DB writes.
  Fix:  Use a Redis distributed lock (e.g., SET sweeper:lock NX EX 25) so
        only one instance runs the sweep per interval.

[L4] HEALTH CHECK DOES NOT VERIFY DB/REDIS CONNECTIVITY
  File: backend/src/app.ts  (GET /health)
  Issue: The health endpoint returns { status: 'ok' } regardless of DB or
         Redis state. A load balancer using this for health checks won't
         detect a broken DB connection.
  Fix:  Add a lightweight DB ping (prisma.$queryRaw`SELECT 1`) and Redis
        ping inside the health handler and return 503 if either fails.

[L5] PAGINATION LIMIT IS NOT CAPPED
  File: Multiple routes (rides, drivers, employees, payouts)
  Code: const limit = Number(req.query.limit) || 20;
  Issue: A caller can pass limit=99999 and dump the entire table in one
         request, causing high memory usage and slow queries.
  Fix:  Cap the limit:  const limit = Math.min(Number(req.query.limit) || 20, 100);

[L6] GOOGLE MAPS API KEY BAKED INTO FRONTEND BUNDLE
  File: docker-compose.prod.yml  (VITE_GOOGLE_MAPS_KEY build arg)
  Issue: The Maps key is compiled into the static JS bundle. Anyone can
         extract it from the browser and use it on their own domain, incurring
         your billing.
  Fix:  Restrict the key in the Google Cloud Console to your production
        domain (HTTP Referrer restriction) and enable only the APIs you use
        (Maps JS, Places, Directions).

[L7] NO INPUT SANITIZATION FOR FREE-TEXT FIELDS
  File: Various routes (description, name, address fields)
  Issue: While SQL injection is prevented by Prisma parameterized queries,
         there is no HTML/XSS sanitization on free-text fields like
         descriptions, issue messages, and incident reports. If these values
         are ever rendered as HTML (emails, PDFs, admin dashboards) they
         could cause XSS.
  Fix:  Sanitize or escape free-text fields at the service layer using a
        library like DOMPurify (server-side) or validator.js strip-tags
        before storing.

[L8] NO AUDIT LOG FOR SENSITIVE ADMIN ACTIONS
  File: backend/src/routes/admin.ts, payouts.ts, drivers.ts
  Issue: Actions like creating tenants, marking payouts as paid, blacklisting
         drivers, and manually assigning rides are not recorded in an audit
         log. There is no way to trace who changed what and when.
  Fix:  Add an AuditLog table (or structured log entries) capturing: actor,
        action, targetType, targetId, before/after values, timestamp.

[L9] DRIVER DOCUMENT TYPE IS A FREE STRING — NO ENUM
  File: backend/prisma/schema.prisma  (DriverDocument.type String)
  Issue: Document type (aadhaar, dl, rc, etc.) is stored as a free string
         with no DB-level constraint. Invalid types like "selfie" or "hack"
         can be inserted.
  Fix:  Convert to a Postgres enum or add a CHECK constraint / Zod enum
        validation at the route layer.

[L10] ANALYTICS PERIOD PARAM IS NOT VALIDATED
  File: backend/src/routes/analytics.ts  (GET /analytics/rides)
  Code: const period = req.query.period as string | undefined;
  Issue: The period string is passed to the service without format validation.
         Malformed values could cause unexpected query behavior.
  Fix:  Validate with Zod: z.string().regex(/^\d{4}-\d{2}$/).optional()
